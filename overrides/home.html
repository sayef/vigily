Experiment tracking · evaluation · drift

Log every run, evaluate it every night, and know by morning what drifted.

vigily is a self-hosted experiment tracker that keeps watching after you stop. Log training runs and evaluations from Python, compare them in a fast web app, run evaluations on a schedule, and get the evidence when behaviour or inputs move. One binary; your storage.

Get started Concepts GitHub

vigily is in beta: the API may still change before 0.1.0.

01

Track runs and long curves

Filter like you think lr<0.01 status:finished loss[val].min<0.25 Reading Fig. 2 Labels sit at the line ends instead of a legend; the run you are looking at is in ink blue.

A small Python SDK logs parameters and metric series. The runs table filters and sorts thousands of runs with a short query language; charts ask for about as many points as they have pixels, so 200 000 points draw as fast as 200. Select runs and they become A, B, C, D, the letters they keep when you compare them.

02

Evaluate on versioned datasets

What is recorded Every item's output, latency and scores, with the dataset version, the target and each evaluator's version. Model keys vigily never holds them: an LLM judge is your own code.

Datasets are content-addressed and immutable. evaluate() runs your target in your process with exact match, regex, numeric, JSON schema or any Python function as the evaluator. Two runs compare item by item, regressions first.

03

Keep watch overnight

The test A paired Wilcoxon test on matched items, with a bootstrap interval. Inputs by PSI and Jensen–Shannon divergence. The baseline Runs that drifted never join it, so a regression keeps being reported until someone fixes it.

Schedules run your evaluation commands on cron in your time zone. Each run is compared with its baseline item by item, and a drift raises an alert in the app and to a webhook, with the items that flipped from pass to fail.

04

One binary, your storage

Where data lives Lance tables written by kv0, in a directory or a bucket: local disk, S3, GCS or Azure.

The web app, the API, the scheduler and the drift monitor are one Rust binary.

# train.py
from vigily import Run

run = Run(experiment="cifar10")
run["hparams"] = {"lr": 3e-3}
for step, loss in train():
    run.track(loss, name="loss", step=step)
run.finish()
# serve the app, the API and the schedules
vigily up --config vigily.toml

# list runs in a terminal
vigily runs "exp:cifar10 loss[val]<0.3"

# run a schedule now
vigily schedules run nightly-intents
05

Questions

All questions
Does any data leave my machine?

No. vigily writes to the directory or bucket you choose, has no telemetry, and never calls a model: evaluators that need one call your own client.

Do I need a database server?

No. Storage is Lance tables through kv0, on local disk, S3, GCS or Azure.

Can the web app start commands?

No. Schedules come only from the server's vigily.toml; the API and the app can read them but not create, change or start them.
